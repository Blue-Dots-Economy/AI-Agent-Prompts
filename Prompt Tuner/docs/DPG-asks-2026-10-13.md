Subject: Blue Dots bots: issues that need a fix on the DPG side (from the 12/10 tracker review)

Hi,

As discussed, these are the tracker items we have marked for the DPG. They cannot be fixed in the bot prompts. Each one is checked against real call transcripts from the Oct 6 and Oct 8 campaigns (Raya call ids in brackets). They are marked "DPG" in column K of the tracker.

1. Job applications fail for everyone (most urgent). Since about Oct 6, every apply_job call returns HTTP 422. With the consent block included, the API says "INVALID_ACTION_EVENT: consent: is not an allowed field". Without it, it says "CONSENT_REQUIRED". So the apply action needs consent but rejects the field that carries it. (17/17 applies on Oct 12, e.g. 444480ed)

2. Recommendation and search do not know what a seeker already applied to (r118). The bot offers jobs the person already applied to; the second apply then fails with ACTION_LIMIT_REACHED. Ask: add an application status (applied / not applied) to each row in the recommendation and search responses, or leave applied jobs out. (114e184e, 61705722)

3. Job search ignores location (r111). get_jobs takes only a text query and get_recommended_jobs only a profile id, so results are not near the seeker. Rows from Kanpur, Gujarat and Karnataka came back in 48 of 142 searches, and two people applied to jobs in Kanpur and Bengaluru (358870b1, 953d2c4b). Ask: a radius or city filter on signals-search using the seeker's profile location or PIN. We have added a bot-side filter that drops out-of-region rows as a stopgap.

4. Under-18 block on profile lookup (r112). get_profile returns 400 U18_NOT_ALLOWED for about 38% of Polytechnic and 12% of ITI contacts (84 calls). In 9 of those calls create_profile then succeeded on the same phone, so the block is inconsistent, and 3 of those people said they were adults. Ask: check the age data behind this check, and decide whether create_profile should apply the same rule.

5. Location is a single field (r121). As agreed, we now write the caller's landmark, area, city, state and PIN as one address string into the profile's location field, which the backend geocodes (tested: lands correctly, e.g. Raj Nagar, Ghaziabad). Separate PIN and landmark fields would still be better.

6. Job posting schema has no salary, qualification or experience (r115). The DKB bot collects them, but job_posting_1.0 rejects these fields, so every posting goes out without them (32/32 posts). Ask: add these fields to the posting schema; the tool will then send them.

7. No API to update or close a job posting (r116). Employers tell the bot a job is filled, but nothing can mark it closed. Ask: an update/close action for job postings.

8. Five-profile cap blocks staffing companies (r120). A staffing company got 409 PROFILE_LIMIT_REACHED on its 6th and 7th postings (121bebdf). Ask: raise the cap for staffing companies, or let old postings be retired.

9. Test postings are live (r117). "Test Job Indsutries", "Vivek Test", "Acme Corp", "ABC Manufacturing", "XYZ Company" and others are live on gzb-signals and were read to seekers; one person applied to Acme Corp. Most share one creator id (40498501). Ask: remove them. The bot now also skips test-looking names.

10. New postings come back as draft. All 30 successful DKB posts returned lifecycle_status "draft". Please confirm drafts are visible to seekers, or make bot posts live.

11. Long pause messages (from the call). The "एक मिनट" hold during get_profile and get_jobs sometimes runs long. We have cut the hold message from the write tools, but tool latency itself is on the platform side. Call ids can be shared on request.
