# Tuner feedback, 14 Oct 2026: what we heard and what changed

Sources: Aryan's "Purple Dots, Taking the bots into five more languages" report, Surabhi's "Purple Dots
Voice Bot, Language testing" sheet, and the review call with Surabhi and Aryan.

## Languages

| Feedback | Gap in the tuner | What changed |
|---|---|---|
| Kannada at full size stopped calling tools, silently | No size check before translating; deploy had one account-wide limit (unset) while the real limit differs per bot | `scripts/prompt_size.py` projects the translated size before any work and checks before deploy; limits are recorded per bot from call evidence (`max_prompt_bytes`, `proven_prompt_bytes`); `raya_deploy.py` refuses past a bot's known failure size. Analyser D116 |
| Instructions and tool calls got translated | The skill said "don't", but the whole file went to the translator | `scripts/speech_split.py`: only spoken lines go to translators; every other line is copied by machine and proven identical |
| Rules still said "speak Hindi/Hinglish"; Marathi slipped into Hindi | Rule lines are English, so they were copied with the language name in them | Those lines are now extracted and rewritten; the build fails if one survives. This also found three such lines in our own demo Marathi bot. D117 |
| Hindi left in Marathi, invisible to script checks | The check asked "right alphabet?" not "translated?" | Same-script lines must come back changed, Hindi marker words fail a Marathi build, the shared danda is no longer a false alarm. D118 |
| Nagpur became Jabalpur | Names were left to each translator | Names pinned once before fan-out; a missing pinned name fails the build. D122 |
| A master mistake would have spread to every language | Nothing said "fix the master first" | New step 0 in /translate-prompt: analyse and fix the master once, before fan-out. D119 |
| Gendered example became two identical lines | Line-by-line translation keeps lines that have no equivalent | Per-language gender rules (`raya/translations/lexicon.json`); duplicates flagged. D120 |
| "The language is very complicated" (Marathi) | No everyday-word list per language, no scan for bookish words | Everyday-word table per language (the nine minimum terms from the sheet), bookish-word warnings, a native listener as the gate. D123 |
| Surabhi's prompt-level checklist | Not in the tuner | `scripts/language_checks.py` runs all nine Prompt rows on any translated file; the Call rows are now in the grading checklist (§19) and the test sheet's language tab |
| Safety statement missed in Marathi and Kannada | No safety check anywhere in the tuner | Required safety-interrupt section (analyser D121), grading checklist §18, and a mandatory safety test case per language |
| Standing checks saw only one prompt | The daily check assumed Hindi and Kannada | It now reads every language from `raya/agents.json` |
| Voice/language ids and two accounts managed by hand | No register; deploy assumed one account | `raya/voices.json` per account; `"account"` per bot in `raya/agents.json`, with a "not found on account X" message |
| Native review is a note, not a gate | | A language is "verified" only after a named speaker signs a side-by-side review tab (safety lines first) |
| Test harness results that looked like bot bugs | Some traps were not written down | /voice-test now lists them (0-second calls, inbound profile on the caller's own number, setup that hides a refusal, late reports, loanwords in grading) |

## Working with the tuner

| Feedback | What changed |
|---|---|
| "Whatever it says flies over my head" | Plain-language rules for every report (root `CLAUDE.md`): the words of the call, not of the tuner; no jargon unless you used it first |
| "I don't know what all it can do" | `docs/WHAT-YOU-CAN-ASK.md`: plain sentences you can type; onboarding ends with it |
| It forgot issues it reported earlier | Every fixing or testing session reads the bot's open-issues list first and updates it last; reports end with "still open from before" |
| A report full of "maybe schema, maybe data" | Reproduce before reporting: place the call that decides, then report what it showed |
| Fix several issues at once | Group issues by root cause and make one fix per cause (each issue still gets its own proving call) |
| Every test run finds new issues | A full baseline run before the first fix; reports say which new issues were caused by the last change and which are old ones seen for the first time |
| Wanted to see the prompt snippets | Every fix report shows the few prompt lines before and after |
| "Run these test cases, N calls each, update the sheet" | /voice-test → "Run a test sheet": reads through the service account, writes Actual / Verdict / calls per row by id, adds new bugs as new rows |

## Test cases

Generated test cases were not in the format people use. /generate-test-cases now delivers a Google
Sheet in the layout of the hand-built "Blue Dots Voice Agents — Test Cases (Oct 2026)" sheet (Read Me,
Bots to Test, one tab per bot family, a language tab per language), and every row must pass
`scripts/testcase_sheet.py lint`: the tester's exact words in the bot's language, the bot's exact line
quoted, "Pass criteria:" including what must not happen, no vague words, Type and Priority set.

Linting our own existing Blue Dots sheet against that bar: TRRAIN 0 errors, DKB 1, KKB Inbound + Slim
4, Maya 5, KKB Outbound 14 (mostly expected responses with no quoted bot line).
