- **`fleet_report.py` does not enforce `--min-calls`.** Line 151 reads `"UNTESTED" if calls <= 0`, while the
  header and the module docstring both promise "at least MIN_CALLS usable calls in the window, else UNTESTED".
  Tonight both Maya bots had exactly 1 call and printed **PASS**. Same shape as the 2026-09-04 self-check bug:
  a bot with no real coverage reads as passing.
- **`fleet_report.py` printed PASS for all 4 covered bots** while `run_runtime_checks.sh` exited 1 with the
  blocking findings above. The blocking-token self-check passes, so the tokens the runtime detectors actually
  emit here (`NO JOBS CLAIMED WITH JOBS SUPPLIED`, `SPOKEN MARKER`, `BAD`, `SUBSTITUTED`) are not in the list
  the fleet verdict consults. A real finding is printed and the bot still shows PASS — the exact 2026-09-04
  failure mode, in a different place.
- **Junk in a live tool description.** `kkb-hi-signals`'s `apply_job` description (1003 chars) is byte-identical
  to the other four KKB signals bots' (983) except it ends with `" X X X X X X X X X X"`. Looks like a leftover
  length/propagation canary sitting in a production tool schema. Parity reports it as info because params,
  required and enums match.
- `record_consent` exists on `kkb-hi-signals-slim` only; absent on kkb-kn-signals, kkb-hi-signals,
  kkb-hi-in-signals, kkb-kn-in-signals. Parity treats a tool present on 1/5 as clean.
