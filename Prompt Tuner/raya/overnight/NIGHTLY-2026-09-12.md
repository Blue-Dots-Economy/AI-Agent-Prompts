## Instrument defect — the fabricated-apply rate is undercounting

**`raya/regression/fab_rate.py` and `raya/regression/fleet_report.py` fetch `/api/call?...&limit=100`
with no `offset` and no pagination.** `apply_result_integrity.py` and `location_integrity.py` do
paginate (`&offset=`), which is why they scanned 526 calls while fab_rate scanned 48. The API caps
`limit` at 100 (`limit=500` → HTTP 400), so the missing pages are simply dropped — silently.

`maya-hi-signals` placed **1720 calls** in this window. Its 100-call page reaches back only to
2026-09-11T15:21:04, so **everything before 15:21 on 09-11 was invisible to fab_rate** — including
`c8ffb645` at 13:22:30, the one genuine fabrication of the day.

| | scanned | success-claiming | fabricated | rate |
|---|---|---|---|---|
| `fab_rate.py` as it ran (row appended to fab-rate.tsv) | 48 | 12 | 0 | 0.0% |
| **paginated re-count, same window** | **364** | **55** | **1** | **1.8%** |

The `2026-09-12` row now in `raya/regression/fab-rate.tsv` (`12  0`) is therefore **wrong**, and the
cumulative figure the script printed — **8 of 47 (17.0%)** — is built on it. Corrected for this
window the cumulative is **9 fabricated of 90 success-claiming calls (10.0%)**.

I have **not** edited the TSV: rewriting measurement history is a human's call. But note the row is
bad data in the one file whose entire purpose is an accumulating denominator, and every earlier row
was produced by the same truncating code — so the pre-existing denominators are under-sampled too,
and **10.0% is itself a floor, not a settled rate**. This is exactly the "clean sample proves
nothing" trap: today would have been reported as a second consecutive zero-fabrication day.

**Ask:** paginate the call list in `fab_rate.py` and `fleet_report.py`, then re-derive the history.

## Second instrument gap — a severe token that cannot fail a bot

`fleet_report.py`'s `BLOCKING` list contains `ROW 1 WRONGLY USED` but **not
`V UNEVIDENCED ALREADY-APPLIED`**, which is the token `apply_result_integrity.py` actually prints for
the same failure — claiming "you already applied" with no evidence. It fired today:

- **`10f5c123-cfd4-4fa5-8e81-9d46a7c3564a`** (2026-09-11T13:25:25, maya-hi-signals) — spoke the
  already-applied line; no apply_job ran twice for the same job and `contact_memory.jobs_applied`
  names none of the jobs attempted. The cause was guessed off an unreadable 422.

The blocking-token self-check reports PASS because it only verifies that every *listed* token is
emitted by some detector — never the converse. A severe token a detector emits but the list omits
can print in full while the bot shows **PASS**. That is the 2026-09-04 `bbdb6eaf` failure mode
still open in a second place. Today it masked nothing only because `maya-hi-signals` had already
failed on `Z`.

Also not in `BLOCKING`: `location_integrity`'s profile-write findings (29 today, below).
