## Inbound job ceiling — investigated to the end, and it is NOT wireable

KKB Inbound Signals presents at most 5 jobs because its whole inventory is 5 `job_id`s hardcoded in
the prompt. The prompt refers to a `get_jobs` tool **four times and that tool does not exist** in
either inbound agent's schema (`get_profile`, `create_profile`, `apply_job`, `update_profile` only) —
the same shape as the `duplicate_check` gap, so I set out to wire it.

**I did not, and it would have made things worse.** The only read endpoint available is
`POST /api/v1/network/item/fetch_local`. Called with the Ghaziabad org key it returns live jobs, but:

- **24 of 25 `jobProviderLocation` values come back masked** — `S***`, `V***`, `R***`
- **`name` (the employer) is `None` on every item**
- the `item_ids` filter is silently ignored — it returns the first N regardless

Masking is by design: these postings belong to provider orgs, and the caller's key is the seeker org,
so non-owned items are redacted. Feeding that to the bot means jobs with no company and no city —
**exactly the input that produced the fabricated jobs on `0a5ec09d`**, where all three supplied
entries had masked locations and the bot read out three roles that were not in the list at all.

So the inbound path needs one of these, none of which is a prompt or tool-wiring change:
1. unmask `name` and `jobProviderLocation` for the calling org, or expose an org-scoped read that
   returns full detail; or
2. give the inbound bots the same curated feed the outbound bots get — outbound receives vetted jobs
   in `${recommendations}` from the campaign system and inbound has no equivalent; or
3. keep a curated inventory in the prompt but make it substantially larger than 5, refreshed on a
   schedule.

Option 2 is the right one — it reuses a pipeline that already produces usable data, and it would also
retire the hardcoded ids that `/raya-reconcile` has to work around.

## TOP RISK, STILL OPEN — the bot sometimes says an application succeeded when it never called the tool

I reported this as fixed twice today. It is not, and it is the most damaging behaviour in the fleet:
a caller who hears "अप्लाई हो गया है" stops looking for work.

`19616c90` (17:36 IST, **after** the tool-schema guard went live at 17:25): the only tool call on the
whole call was `get_profile`. There was no `apply_job` at all, and the bot said
**"अप्लाई हो गया है"** and moved on to the service-provider offer.

Rate: roughly **1 call in 7** where an apply is discussed. Known instances today — `29c4f152`,
`1fe093a9`, `4b0ea64d`, `19616c90`, plus one more in the morning window.

Three mechanisms tried, in this order, each verified working on several calls and each eventually
failing:
1. prose rule that the success line may only appear in the same turn as the tool result;
2. declaring parentheticals non-speech and marking every tool annotation `*(NOT SPOKEN — …)*`;
3. the constraint moved into the `apply_job` tool description.

Under our own rule I am not writing a fourth wording. What is left is not a prompt change:

- **Let the platform speak the confirmation.** `apply_job` already takes a `hold_message` that Raya
  utters when the tool is actually invoked. If the SUCCESS sentence were delivered the same way — by
  the runtime, on a real result — the model could not fabricate it. This is the clean fix.
- **Or fail closed:** have the runtime reject/flag an assistant turn containing the success line when
  no successful `apply_job` result exists in that turn.

Detection is in place either way: `apply_result_integrity.py` check Z catches every instance, and
`fleet_report.py` treats it as blocking, so the fleet reads FAIL while this is live. That is correct
— it should not go green until this is fixed.
