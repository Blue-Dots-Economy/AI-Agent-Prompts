### 2. HARNESS DEFECT (new, defect 10) — a crashed detector reads as a clean bot

`fleet_report.py` reported `kkb-hi-in-signals ... PASS ... none` on **both** of tonight's runs while
`inbound_location_consent.py` was printing the blocking finding above for that exact bot.

Root cause, confirmed by code inspection and reproduced live:

```python
def run(cmd):
    p = subprocess.run(cmd, cwd=REPO, capture_output=True, text=True)
    return p.stdout + p.stderr        # returncode is DISCARDED
```

The detectors die on **HTTP 429** under this suite's own concurrency. When one does, `run()` returns
a Python traceback instead of findings, the verdict loop finds no BLOCKING token in it, and the bot
is printed **PASS**. A detector that never graded a single call is indistinguishable from a detector
that graded every call and found nothing. I reproduced the 429 death of
`inbound_location_consent.py` twice standalone after the fleet run.

This is the same shape as the 2026-09-04 consent violation on `bbdb6eaf`: a real finding printed,
and the bot still PASS. It is the sibling of defect 8 (`call_count()` can't tell "no calls" from
"API error") and defect 9 (no backoff), both raised 2026-09-17 and still unfixed. Fix wanted:
fail loudly on a non-zero detector exit — a detector that errored must render the bot **UNGRADED**,
never PASS.

**Until that lands, no `fleet_report` PASS should be believed on a busy night.**
